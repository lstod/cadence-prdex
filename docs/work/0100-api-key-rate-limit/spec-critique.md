# Spec critique: Rate-limit API endpoints per API key

- Spec: [spec.md](spec.md)
- Critic: spec-critic (Claude Code)
- Date: 2026-10-08

## Findings
| # | Kind | Severity | Finding | Evidence | Disposition |
|---|---|---|---|---|---|
| 1 | weakness | important | The spec fixes the blocked-key reset value as the literal `null` in the Format table, AC-6 and Example, but also leaves it open under Open questions. If lstod picks option (b), leaving the header out, that choice contradicts AC-4, which requires all three headers on every authenticated response. Option (a) puts a non-integer into a header the same table defines as "integer Unix seconds", so clients that parse it as an int will fail on blocked keys. Today the open question cannot be resolved without changing AC-4 or AC-6. Pick one option and state the AC-4 exception, or the parse caveat, before approval. | Format "Headers" table, row `X-RateLimit-Reset`; AC-4; AC-6; Open questions; intent.md Open questions | open question: kept for lstod; the open question now states, for each option, the change to AC-4 and AC-6 and the parse caveat. The Format notes that `X-RateLimit-Reset` is an integer for every key that is not blocked, AC-4 limits "integer Unix seconds" to keys that are not blocked, and a Risks bullet records the parse caveat. |
| 2 | weakness | important | AC-8 depends on an `ApiKey` row existing in Postgres. Nothing in the app creates one: no route writes `ApiKey`, there are no migrations, and setting `requests_per_minute` is a non-goal. The spec never says how the key is seeded or how the tables are created. It also does not require the 101 requests to start just after a minute boundary. If the run starts at, say, :50, the window resets partway through, request 101 returns `200`, and the evidence can't show the AC. | AC-8; Verification AC-8; `app/repositories/api_keys.py:24` (only `create`, unused by any route); AGENTS.md "There are no migrations"; Non-goals "Any API or admin route to set `requests_per_minute`" | accepted: AC-8 now names the setup (tables created, one `ApiKey` and one workflow seeded) and requires the loop to start within the first 5 seconds of a minute. Verification AC-8 describes one-off setup commands recorded in `evidence.md`. Added Context bullets for `app/repositories/api_keys.py:24-28` and the missing migrations, a non-goal for committed seed scripts, and a Risks bullet on AC-8 timing. |
| 3 | failure mode | important | The spec claims headers appear on a `422` the route raises after authentication. That holds only when the body is well-formed JSON that fails the schema. FastAPI parses the JSON body before it resolves dependencies. So `POST /workflows/{id}/run` with a valid key and a malformed body such as `{"triggered_by":` returns `422` before `api_key_auth` runs: no `X-RateLimit-*` headers, and the request is not counted. A test written to the Format line "errors the route raises afterwards, such as `404` or `422`" fails, or the builder adds an exception handler to force headers onto a response for a key that was never authenticated. Name schema-invalid `422` only, and state that malformed-JSON `422`s carry no headers and are not counted. | Format "Headers" paragraph; `app/routes/workflows.py:157` (`payload: WorkflowRunIn` body); AC-4 | accepted: the Format Headers paragraph and AC-4 now name only a `422` for a well-formed JSON body that fails the schema, and state that a malformed-JSON `422` is not authenticated, not counted, and has no headers. Added a failure case to the Example, a non-goal, and a malformed-JSON test to Verification AC-4. |
| 4 | alternative | minor | A pure ASGI middleware that wraps `send` and adds the headers from `scope["state"]` at `http.response.start`, instead of `@app.middleware("http")`, which is Starlette's `BaseHTTPMiddleware`. Gain: no `BaseHTTPMiddleware` overhead and no streaming or contextvar problems, and it covers every response the app stack produces. Cost: about 20 more lines of lower-level code that a reviewer has to check. Neither design puts headers on a `500` from an unhandled exception: `BaseHTTPMiddleware` re-raises, and `ServerErrorMiddleware` sits outside user middleware. The spec's "whatever the status" should exclude `5xx`. | Spec section 4 last paragraph ("An HTTP middleware registered in `app/main.py`"); Design decisions "Headers set by a middleware"; `app/main.py:7` | accepted: the `5xx` exclusion. The Task, Format, and AC-4 now cover only responses with a status below 500, with a non-goal for `5xx`. The ASGI alternative itself is not taken and recorded under Design decisions: every API-key route is a plain JSON route with no streaming, so `@app.middleware("http")` is enough. |
| 5 | alternative | minor | Keep blocked keys out of the limiter. `api_key_auth` returns the blocked `429` itself when `requests_per_minute is not None and <= 0`, and `RateLimiter.hit(key_id: int, limit: int)` always takes a positive int. Gain: removes the double meaning of `None`. Today `requests_per_minute=None` means 100 while `hit(..., limit=None)` means blocked, so passing `key.requests_per_minute` straight to `hit` would block every default key. It also means a future Redis limiter that satisfies the Protocol does not have to reimplement blocking. Cost: the code that builds a `RateLimitDecision` for a refusal is split across two modules, and `reset: int \| None` is needed only in the auth layer. | Interfaces block (`hit(self, key_id: int, limit: int \| None)`, comment "limit=None means blocked"); Format "Effective limit" table row `None` -> 100 | accepted: `effective_limit` returns `0` for a blocked key, `hit()` takes a positive `int` and raises `ValueError` otherwise, `RateLimitDecision.reset` is `int`, and `api_key_auth` refuses blocked keys without calling the limiter. Added a Design decision, and Verification AC-6 checks the limiter is never called. |
| 6 | untestable AC | minor | AC-8's "shown with `curl -i` in real time" cannot be checked from a pasted transcript: neither timing nor ordering is provable. It is testable if the evidence comes from a scripted loop that prints `date -u +%s` before each request and the response status and headers after it, starts within the first seconds of a minute, and shows request 1, request 101, and the first request after the boundary. | AC-8; Verification AC-8 | accepted: AC-8 and Verification AC-8 now require a scripted loop that prints `date -u +%s` before each request, starts within the first 5 seconds of a minute, and records request 1, request 101, and the first request after the boundary. |
| 7 | missing non-goal | minor | Nothing stops a builder from adding `Depends(api_key_auth)` to routes that lack it today, such as `POST /workflows`, `/runs`, or the unmounted integration and admin routes, so that "every API-key endpoint" gets limits. That is an auth change outside the intent. The current non-goal excludes rate limiting those routes but not putting them behind API-key auth. | Non-goals bullet 1; `app/routes/workflows.py:86-90` (`create_workflow` has no auth); AGENTS.md module map (unmounted `app/routes/admin/`, `app/routes/integrations/`) | accepted: added a non-goal ruling out API-key auth on any route that lacks it today, and a Context bullet for `app/routes/workflows.py:86-90`. |
| 8 | missing non-goal | minor | Validating or constraining `requests_per_minute`, for example a `CheckConstraint`, a model validator, or a change to the column in `app/models/api_key.py`, is not ruled out. Such a change needs a schema change in a repo without migrations. The spec only says no route sets the value. | Non-goals; `app/models/api_key.py:14`; AGENTS.md "No migrations" | accepted: the non-goal now rules out any validation, constraint, or column change for `requests_per_minute`, and Constraints rule out any change to the `ApiKey` model or any table. |
| 9 | unbacked claim | minor | Context cites `get_idempotency_store` at `app/routes/workflows.py:50-55`. Those lines hold the `_default_idempotency_store` instance (51-53) and blank lines. The provider `def get_idempotency_store` is at lines 56-57. | Context bullet 5; `app/routes/workflows.py:51-57` | accepted: the citation now reads `app/routes/workflows.py:51-57`, covering the default instance and the provider. |
